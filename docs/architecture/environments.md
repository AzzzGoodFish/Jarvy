# Work environments

[Index](../index.md) · [Bot runtime](runtime.md) · [Tools and prompt](tools-and-prompt.md) · [Decisions](../decisions.md) (A50, A57)

A work environment is where a Bot's `bash`, `read`, `write` and `edit` run. The Bot itself — its Pi session, model calls and chat tools — always runs in Jarvy.

Two words, kept apart:

- **Workspace**: the Bot's own folder, `bots/<id>/`, which every Bot has and never shares; it tells people where the Bot's private, lasting files are. Its tools see `workspace/` inside it; its sessions and History sit beside that and never enter an environment.
- **Work environment**: where its file and command tools run. Every Bot's default is its own **sandbox**, which Jarvy makes and manages for it alone (a Docker container; later a VM; the code calls it a `computer`), where the workspace is mounted as `/workspace` (A68). **External environments** are places a Bot is granted and switches to, never a default: the **SSH machines** the owner adds (A57) and the **computers** that connect themselves with the desktop client (A96). The computer running Jarvy is one of them when the owner adds it; Jarvy never runs a Bot's commands itself. Without Docker a Bot still has its sandbox as its default; its file and command tools fail until Docker can be used, and its chat tools work as usual (A84).

People read Docker 沙箱 / "Docker sandbox"; a Bot reads "your own computer" and, in `environments.list`, "your sandbox". An SSH machine goes by the name the owner gave it.

## Layers

| Layer | Code | Knows |
| --- | --- | --- |
| Interface | `shared/environment.ts` (`WorkEnvironment`) | run a command with streamed output, read a file or its first bytes, write, make a directory, check a path, close |
| Execution | `infra/env/` | Pi Durable's `NodeExecutionEnv`, pi-env, the docker command line for Bots' sandboxes, `ssh`/`ssh-keygen` for SSH machines (`ssh.ts`), and the WebSocket relay to computers (`device-link.ts`, `device-daemon.ts`); nothing else imports pi-env or Pi Durable (`check-boundaries`) |
| Tools | `infra/pi/environment-tools.ts` | Pi's tool definitions with operations on the interface |
| Rules | `service/bot/environments.ts` (`BotEnvironments`), `service/bot/computers.ts` (`Computers`), `service/bot/machines.ts` (`SshMachines`), `service/bot/devices.ts` (`Devices`) | which environment a Bot is in; the life of Bots' sandboxes; adding, checking and removing SSH machines; pairing computers, their shells and paths |
| Kinds | `service/bot/kinds/` (`sandbox.ts`, `ssh.ts`, `device.ts`, A65) | what differs by kind and nothing else: how to reach it, what the Bot calls it, what a switch does first, which fields `environments.list` adds, what the Bot is told about it, and what an open environment is keyed by |

`infra/env/durable.ts` adapts any Pi Durable execution environment to the interface: results become values or thrown errors, an abort or a timeout becomes the `aborted` / `timeout:<s>` error Pi's bash tool words, and `close()` releases what it holds.

`WorkEnvironment` also says whether it is `local`: it runs on the machine Jarvy does. Only there are Pi's own file paths the tools' paths, so a long command output needs no moving (`infra/pi/environment-tools.ts`) and a temporary file is written in the workspace (`service/bot/workspace.ts`).

## Kinds

`BotEnvironments` never asks what kind an environment is. `kinds/index.ts` maps each `EnvironmentKind` to one entry with `open` (the `WorkEnvironment`), `place` (the name the Bot knows it by and the directory its tools start in), `ensure` (a switch starts a sandbox first), `connects` (a switch to an SSH machine connects and stays where the Bot was if its directory isn't there), `summary` (its name in `bots.list`), `describe` (the extra fields in `environments.list`: a sandbox's state, a machine's address and description), `about` (what the Bot is told when it switches there) and `signature` (a machine reopens when the owner changes its directory). `home` and `grantable` say whether it can be a default and whether the owner grants it.

A new kind is one file there and one row in `KINDS`; the compiler names the fields it lacks.

## How the tools use it

- `environmentTools(current)` builds Pi's bash, read, write and edit with their pluggable operations and registers them as custom tools under the built-in names, so they replace Pi's local ones. Schemas, output truncation, descriptions and codemode's nested calls stay Pi's.
- Each call asks `current()` for the Bot's environment when it starts and keeps it to the end, so a change of environment needs no new session and an edit never reads in one place and writes in another.
- Pi resolves a tool's paths against the run's working directory; the tools see the directory of the environment the call runs in instead.
- `read` tells pictures from their first bytes (`image-kind.ts`, Pi's own rules), wherever the file is.
- A command gets the environment of the place it runs: the container's, or the SSH login's.

## Where a Bot works

Storage (v20): `environments` rows belong to a person; a Bot has a default (`home_environment_id`) and a current environment (`current_environment_id`). Since v29 every Bot's default is its own sandbox's row (A68): one is made with each Bot, and at startup for any live Bot without one (the agent Bot on a new installation, or one restored). `BotEnvironments.current()` reads the current one at every tool call and opens it on first use. The one a Bot leaves closes once the operations still running there end, so a switch never cuts a command short.

- **Its sandbox** (`computer`): a Docker container only that Bot uses, or a full Linux virtual machine run by libvirt and QEMU where the owner chose one (A101; below). Commands get the sandbox's own environment variables.
- **An SSH machine** (`ssh`): pi-env over `ssh`, logging in with the key Jarvy made for it (below). Commands get the login's own environment.

A new Bot gets its sandbox when it is created (`POST /bots`, the agent's `bots.create`): the row at once, the container in the background when Docker is there. There is no other default to choose, so neither takes an environment, and the new Bot's first setup asks only for a model.

## The Environments page

The rail's third entry (A87, A89), beside the agent Bot's page and the chats: where Bots work, in one place (`web/environment/Environments.tsx`).

- **On the left**, one list of every environment, one row each, no groups: the SSH machines first, with their address, then each Bot's sandbox, 「Jarvy 的沙箱」 / "Jarvy's sandbox", with its type (容器 or 虚拟机) and its state as a dot (running green, preparing amber, stopped grey, failed or without Docker red). An icon says the kind (container, VM, machine). Each row ends with the Bots working there now (their current environment), overlapping past one and asleep when stopped, so a Bot that switched to a machine is on the machine's row and its sandbox's row is empty. Above the list, as on the chat list and in the same place, + adds a machine and a search box filters the rows: a machine by its name or address, a sandbox by its Bot's name; 「无匹配的环境」 when none fits, Esc clears it.
- **The same look as the chats**: the list's names in the DM list's weight, the page title in the chat header's, and and the right side on the form scale Settings and Bot info share: inputs and body text at the chat's 14 px, labels and notes at 13 px.
- **On the right**, the one picked (the first row until something is), with a header switch between **Overview** (who works there, a sandbox as Bot info's 环境 tab shows it with its ports, a machine or computer with its details), **Terminal** (persistent multi-terminal sessions, A103) and **Files** (direct file browser and streaming upload/download, A104); or the form to add one. The pick and active tab are kept while the page is away and lost on a reload. Each sidebar row shows a badge with its active terminal count when at least one is running.
- **Interactive terminals** (A103): `/api/terminals` (REST) and `/api/terminals/:id/ws` (owner session cookie + same-origin WebSocket) let the owner open multiple persistent terminals in any Bot sandbox (container or VM, auto-starting a stopped sandbox), SSH machine, or connected computer (Linux/macOS via `pi-env` `openTerminal`, Windows via the connector's native ConPTY channel). `TerminalService` keeps each PTY alive on the server with `@xterm/headless` + `@xterm/addon-serialize`, so closing a tab, switching pages or losing network restores the exact screen and scrollback on reconnect without requiring `tmux` on target hosts. Stopping, resetting, switching or removing an environment closes its terminals.
- **Direct file browser & transfer** (A104): `/api/environments/:id/files` (`GET`, `DELETE`), `/download`, `/upload`, `/mkdir`, and `/rename` let the owner browse directories, stream arbitrarily large uploads/downloads, create folders, rename and delete across all four environment types without routing files through chat. `EnvFileService` (`service/env-files.ts`) depends only on the transport-agnostic `EnvironmentFs` interface (`shared/env-files.ts`), pools dedicated short-lived connections per environment (isolated from Bots' tool connections, 5-minute idle TTL), streams downloads over a single reader handle, stages uploads atomically via temporary `.part` files, and refuses stopped sandboxes with `sandbox_stopped` until the owner explicitly starts them.
- **On a phone** the list fills the screen above the tab bar; a pick opens over it with a way back, and without the tab bar.
- Bot info keeps its 环境 and 授权 tabs. Settings has no machines page.

## In Bot info

Bot info's 环境 tab has its sandbox; the machines it may use are on the 授权 tab:

- **Its Docker sandbox**: Docker 沙箱 / "Docker sandbox", its state, and a line saying which machine the Bot is on when it switched to one; then its type, 容器 or 虚拟机 (A85), and what it is made of (the container's name, its image and the workspace's mount point, `/workspace`), its resource limits and, while it runs, what it uses of each against them (A75; a VM's with its Docker disk and what it takes of this machine, A85), Start or Stop and Reset; when Docker can't be used, in their place, one sentence: why (not installed, not running, no permission, or something else), that a sandbox can't be started for the Bot, and that without one it can't read or write files or run commands. How to fix it is the agent Bot's to explain (its setup skill), not this page's (A84). Stopping closes what the Bot left running and resetting removes what it installed, so both ask in place first (Bot info is itself a dialog).
- **授权 › 外部环境**: the SSH machines granted to the Bot, by name with their address, each removed with ✕; 添加 picks more of the owner's (searched by name or address), and with none added at all offers Add machine, which opens the Environments page at the form to add one. Taking one back while the Bot is there sends it back to its sandbox. The same tab lists its secrets ([secrets](secrets.md)).

## Grants and switching

- **May use**: a Bot may be in its sandbox and on the SSH machines its owner granted it (`environment_grants`; `PUT /bots/:id/environment {machineId, granted}`, or from the machine on the Environments page). For the agent Bot, `PUT /bots/:id/environment {sandboxId, granted}` also grants other Bots' sandboxes, and `environments.enter` can ask the owner for a permanent or single-run (`run_id`) grant on a card (A93). Otherwise a grant lasts until it is taken back; only the owner grants, not the agent Bot.
- **Switching**: `environments.list` gives the Bot's sandbox and default and every SSH machine of the owner's, each machine with `granted` (whether the Bot may use it), with ids, names, the directory its tools start in, its default, a sandbox's state, and an SSH machine's address and description; `environments.switch` moves it, like `cd`, until it switches back, starting a stopped sandbox first and answering with the directory and what the Bot can do there; a machine it may not use is refused, naming `environments.request` and its id. Bot info shows which machine a Bot is on when it switched to one.
- **Telling the Bot**: the system prompt's Workspace and Work environment sections are the same for every Bot (A68): its workspace on its own computer, that other members work on their own machines and can't reach its files, addresses or what it starts (nor it theirs), that files go across as attachments, and how to switch to an external environment. They never change with a switch, so the prompt cache survives one; each batch ends with `<environment name directory/>`, where it is now ([envelope](envelope.md)). What the owner changes reaches the Bot as a `change` delivery ([delivery](delivery.md), A41), told once and kept in its History: a move (taking an SSH machine back, or deleting it, while the Bot is there) interrupts a running turn like an @, stopping its commands but not the processes it left running in the background, and starts a new one with the news; a Bot that isn't running, and a change of access alone, hear of it with their next batch.
- `bots.list {environments: true}` adds each Bot's default, current and usable environments.

## A Bot's sandbox

- **Image**: built on this machine from the Dockerfile in `infra/env/computer-image.ts` (Playwright's Ubuntu 24.04 image with its browsers, plus the matching `playwright` package found by any script, CJK fonts, git, Python with its headers, build tools and sudo; npm installs globally under the user's home), tagged `jarvy-computer:<hash>` of the Dockerfile and the owner's ids, so a change builds a new one, after which older ones no container uses are removed. One image serves every Bot and is stored once, so what most Bots need belongs in it and the rest is theirs to install. The first build pulls the base and takes minutes; its output goes to `computers/build.log`.
- **Container**: `jarvy-<data>-<bot>`, labelled with a hash of the data directory and the Bot's id. It runs `sleep infinity` with `--init` as user `bot`, which has the owner's user and group ids (so its files in the workspace are the owner's) and passwordless sudo. The Bot's `workspace/` is mounted as `/workspace`, its directory there and `bot`'s home, so its settings and caches (`~/.ssh`, `~/.gitconfig`, `~/.cache`) stay with the workspace and outlive a reset; a container from an older image has its home moved in place when Jarvy first connects to it, keeping what was installed; `computers/bin` (the pi-env daemon, kept current from the package at startup) is mounted read-only at `/opt/jarvy`.
- **Reaching it**: one pi-env connection per Bot over `docker exec -i <container> /opt/jarvy/pi-env`, carrying every request; pi-env starts it again after it is lost. If a call fails because the container stopped behind Jarvy's back, Jarvy starts it and tries once more.
- **Life**: made when the Bot gets it, in the background (`preparing`); started by the next tool call or the Start button; kept running until the owner stops it with the Stop button, since stopping closes what the Bot left running; a reset removes the container, so the next start makes a fresh one — software installed with sudo goes, `/workspace` stays; deleting the Bot removes the container. Containers keep running when Jarvy stops, so background work survives a restart. A sweep every minute learns container states and removes containers of this data directory that no Bot has.
- **Resource limits** (A75): a memory limit (256 MB up to the machine's memory, swap limited with it) and a CPU limit (0.1 up to its CPU count), none by default, kept in the computer's `connection` as `memory` (bytes) and `cpus`. `PUT /bots/:id/computer/limits {memory, cpus}` (null for none) applies them with `docker update` to a container that exists, running or not, and `docker run` gives them to one made later; Docker can't take a limit off, so none there is the whole machine until the next container. `GET /bots/:id/computer/resources` gives the usage of a running sandbox (a container's from `docker stats`, a VM's as below) and the machine's CPUs and memory (`docker info`); Bot info shows each against its limit, or the machine's whole without one, with a bar. With a limit set, `environments.list` and a switch to the sandbox name it to the Bot.
- **Type** (A101): a container (Docker, the default) or a full Linux virtual machine (libvirt + QEMU, `qemu:///system`), kept in the computer's `connection` as `type: "vm"`. Bot info › 环境 has a row 类型 with both; 虚拟机 can be chosen once libvirt and KVM pass their check (`GET /environments/vm`, first asked when the tab opens, cached; `POST /environments/vm/check` again), and otherwise its row says why: libvirt/QEMU not installed, libvirtd stopped, no permission (`libvirt` group), missing `qemu-img`/`cloud-localds`, no KVM, KVM taken by another hypervisor (VirtualBox), or another failure. Docker and libvirt availability are independent, so VM sandboxes work even without Docker on the host. `PUT /bots/:id/computer/type {type}` asks in place first, then recreates the sandbox while preserving `/workspace` losslessly in both directions (importing host `bots/<id>/workspace` into `workspace.qcow2` on container→VM, exporting back before removing volumes on VM→container); published ports are taken down, and the new one starts. See **VM sandboxes** below.
- **States** shown in Bot info: `preparing`, `running`, `stopped`, `failed` (the start failed; the code is kept), `unavailable` (Docker can't be used for a container, or libvirt/KVM can't be used for a VM; `error` says why).
- **Docker that can't be used** (A84): `docker version` tells the cases apart — no `docker` command, no daemon answering, the daemon refusing this user (permission denied), anything else with what Docker said. The log says it once per reason. While it can't be used, Jarvy looks again every 30 seconds and takes Docker up when it can, without a restart; a sandbox that a Bot tried to use meanwhile shows as it is then, not as failed. The Bot reads why in its sandbox's line in `environments.list` (`problem`), in what a switch there and a failing tool say, and in its batches' `<environment problem>`.
- **Network** (A74): container sandboxes share `jarvy-<data>`, a Docker bridge network with traffic between containers off; VM sandboxes share a libvirt NAT network (`jarvy-<tag>`) with an `nwfilter` (`jarvy-<tag>-iso`, `clean-traffic` plus subnet isolation) that blocks VM-to-VM traffic while allowing the host gateway (`host.docker.internal`) and the internet. Services of this machine that listen on all its addresses are reachable that way; those on its loopback only are not.
- **Published ports** (A74): `ports.publish {port, name, description}` gives a port of the sandbox a port of Jarvy's from the owner's range (Settings → Network, default 12600–12699), kept in `published_ports`. `api/published.ts` listens on each like on Jarvy's own port (both protocols, its certificate) and forwards requests, WebSockets included, to the sandbox's address on the network (container IP or VM DHCP IP): for the owner's browser signed in to this Jarvy, and for this Jarvy's sandboxes by the address they come from; others get a sign-in page. Jarvy's session cookies are taken out of what goes to the service and out of what it sets. Bot info lists them as Port forwarding (`GET /bots/:id/ports`, `DELETE /bots/:id/ports/:port`), rows that open in place, each with Jarvy's port for it (the sandbox's is shown open, last) and a state read from the sandbox's `/proc/net`: `live`, `local` (127.0.0.1 only), `idle`, `stopped`. A reset or deleting the Bot unpublishes its ports.
- **VM sandboxes** (A101): full Ubuntu 24.04 Linux virtual machines managed through `virsh -c qemu:///system` (`infra/env/libvirt.ts`, `infra/env/vm-template.ts`, `infra/env/vm-guest.ts`, `service/bot/computer-vm.ts`), requiring only standard apt packages (`libvirt-daemon-system`, `qemu-system-x86`, `qemu-utils`, `cloud-image-utils`) and membership in the `libvirt` group — no root setup scripts. Storage lives in a Jarvy-scoped libvirt directory pool (`/var/lib/libvirt/images/jarvy-<tag>`) so host home-directory permissions never block `libvirt-qemu`. On first VM start, Jarvy automatically downloads the official Ubuntu 24.04 cloud image (overridable via `JARVY_VM_IMAGE_URL`, respecting host proxy env vars), boots an ephemeral builder VM, provisions Node, Python, git, build tools, CJK fonts, Playwright + Chromium, Docker Engine + Compose, `iproute2`, `tmux` and `jq` over SSH (logged to `computers/vm-build.log`), cleans guest identity and clones it into a content-addressed read-only backing volume `base-<hash>.qcow2` (unused older templates are pruned). Each VM gets two thin-provisioned virtio qcow2 disks with `discard="unmap"`: a 64 GB OS disk (`<name>-os.qcow2`, COW over `base-<hash>.qcow2`, with a 2 GB `/swapfile` and `/var/lib/docker`) and a dedicated 64 GB ext4 `/workspace` disk (`<name>-workspace.qcow2`), plus a NoCloud `seed.iso` that injects fixed SSH host keys and Jarvy's per-VM ed25519 client key into `/etc/jarvy/bot_authorized_keys` (sealed in `environments.key` / `host_keys`, no schema change). Domains use `<cpu mode='host-passthrough'/>` (exposing nested KVM when the host enables it) and ACPI shutdown on Stop. Tools reach the VM through `pi-env` over SSH (`sshEnvironment(..., "computer")`). Reset removes only the OS disk and seed ISO, preserving `workspace.qcow2`; switching back to a container or deleting a Bot with `keepFiles` exports `/workspace` atomically back to host `bots/<id>/workspace` before removing volumes. Default size is 4 GB and 2 vCPUs (minimum 1 GB and 1 vCPU); changes apply on the next boot. Live memory, CPU and combined disk usage are read inside the VM over SSH, alongside host QEMU `VmRSS` and qcow2 allocated blocks (`virsh vol-info --bytes`).
- **Files from the chat** come into an environment only by `files.get`; files a Bot sends are read from its current environment, whichever it is.
- **Long command output**: Pi keeps the whole of a truncated bash output in a temporary file on this machine; for a Bot elsewhere the file is moved into its environment's temporary directory (`temp/` in its directory; on an SSH machine `~/.cache/jarvy/<bot>/`) and the result names that path. `history.read` with `to_file` and `files.get` write there too.

## SSH machines

Machines the owner adds over SSH (A57), listed on the Environments page (below) and granted to Bots one by one. The computer running Jarvy is added the same way when Bots should work there (A68), at `127.0.0.1`.

- **Adding**: the owner gives host, port (22), user, an optional name (default `user@host`), start directory (default the user's home; `~/…` is under it) and description (several lines, up to 2000 characters: what it is for, what to watch out for). Jarvy scans the host's keys without logging in and shows their fingerprints to check against the machine. Then the owner lets Jarvy in one of two ways (A59):
  - **The password**: Jarvy makes an ed25519 key pair (`ssh-keygen`), logs in with the password, appends the public key to `~/.ssh/authorized_keys` (once; its comment is `jarvy-<machine id>`), and logs in again with the key to learn the system and home. When the machine refuses the key (`PubkeyAuthentication no`), Jarvy logs in with the password instead and keeps it sealed; the key stays installed for when keys are allowed. A machine that takes no passwords says so (`ssh_password_refused`) and the owner picks the other way.
  - **Adding the key themselves**: Jarvy makes the key pair and shows its public line to copy (kept in memory for an hour, under a `keyId`); the owner adds it to `authorized_keys` and Jarvy checks a login with it (`ssh_key_refused` if it isn't there).

  Either way the machine is saved only after a login works. A step that fails saves nothing, and a key Jarvy installed is taken off again.
- **Asking**: `environments.request` posts the same check as a card in a chat with the owner, who types the password there or adds the key it shows; the machine is added and granted to the Bot before the card settles. A wrong password leaves the card open. A machine already added only needs Allow, asked for by its id from `environments.list`; one the Bot may already use returns at once.
- **Keys**: the private key is sealed under the master key (`environment:<id>`, A52) and written to an owner-only file under `ssh/` in the data directory only while a connection is open, with a `known_hosts` file holding the accepted keys under the alias `jarvy-<id>`. The public line is read back from the private key (the OpenSSH format keeps it in the clear) and shown with a copy button in the machine's details.
- **Password logins**: a kept password is sealed too (`environment-password:<id>`). While a connection is open it sits in an owner-only file beside the key, read by an askpass helper; pi-env is given a wrapper `ssh` that puts `BatchMode=no`, password authentication and no public key before pi-env's own options (ssh keeps an option's first value). In the details, 更新密码 checks a new one with a login before keeping it, and 切换为密钥登录 (as does Check fingerprint) tries the key: once it works the password is dropped. Jarvy reads neither `~/.ssh/config` nor `~/.ssh/known_hosts` (`-F /dev/null`), so a machine is reached exactly as it was added. `ssh/` is cleared at start.
- **Details**: a machine picked on the Environments page has three parts, split by lines: the machine (name, start directory, description and their Save), how Jarvy reaches it (fingerprints with Check fingerprint, login), and the Bots that may use it, as tags that wrap however many there are; then Delete machine. Above them, which Bots work there now.
- **Host keys**: checked strictly. A machine that presents another key is refused (`ssh_host_key_changed`); on the Environments page, Check fingerprint scans it again and, when the key changed, shows the new one to accept.
- **Working there**: a Bot granted a machine switches to it; the switch connects first and checks the start directory exists, else the Bot stays where it was. pi-env's daemon is deployed to the machine on first use. Changing the start directory moves Bots working there at their next call. Jarvy's files for a Bot go in `~/.cache/jarvy/<bot>/` there, never in the start directory.
- **Deleting**: removes Jarvy's line from `authorized_keys` first, logging in the way the machine is reached; when the machine can't be reached the owner may delete it anyway and remove the line by hand. Bots working there go back to their default and are told; the sealed key and password are dropped.
- **Systems**: Linux and macOS.
- **Limit**: Pi's `write` and `edit` look a path up on the machine running Jarvy before writing (to queue changes to one file). A path that exists there but can't be read by Jarvy's user, such as `/root/...` when Jarvy runs as someone else, makes them fail; `bash` still works there.

## Computers

Computers the owner's desktop client connects (A96), 「电脑」 in the interface and `device` in code. The client — the Electron app later, the command-line connector (`src/connect/`, built to `dist/server/connector.mjs` and served at `/api/devices/connector.mjs`) now — runs on the computer as the person signed in there.

- **Pairing**: the first run checks Jarvy's root certificate by its fingerprint (HTTPS), signs in as the owner and registers the computer (`POST /api/environments/devices {name}` → the device and its token, once). The token (256-bit) is kept by the client (`device.json`, owner-only; `safeStorage` in the desktop client); Jarvy keeps its SHA-256 in `environments.token_hash`. The Environments page's + offers 电脑 beside SSH 机器 with the commands for Windows and for macOS and Linux.
- **Connection** (`infra/env/device-link.ts`): the client opens `wss://…/api/devices/connect` with `Authorization: Device <token>` and says `hello` (protocol, platform, arch, home, shells, client, capabilities, paused); Jarvy answers `welcome`. One connection per computer: a newer one replaces it (close 4000); an unknown token is refused with 401 or closed 4003; another protocol gets an `error` and 4001. Pings every 30 s; a client reconnects after 1 s, doubling to 30 s.
- **Running tools**: pi-env's `Connection` runs a tiny relay (`node -e`) that joins a local Unix socket; Jarvy sends `open {ch, args, bot}` to the client, which starts the daemon (from `/api/devices/daemon?platform&arch`, checked by SHA-256, kept under its hash) and joins its standard input and output to the channel. `exit` or `close` ends it. Files and long outputs go in `~/.cache/jarvy/<bot>` (`%LOCALAPPDATA%\Jarvy\bots\<bot>` on Windows).
- **Shells and paths** (`service/bot/devices.ts`): automatic is bash (Git Bash on Windows) when there is one, else PowerShell (pwsh first); the owner can pick one in the computer's details, and the Bot is told which. A PowerShell command runs as a temporary `.ps1`. On Windows, `C:\x` and `/c/x` are translated both ways for the file tools.
- **Offline and paused**: every tool call checks that the computer is connected and not paused in the client, and otherwise answers which of the two it is; pausing in the client also stops its running daemons.
- **In the page**: computers come first in the list (system and an online / paused / offline dot), searchable by name and system; the details hold name, start directory, description, system, state, shell, client, the Bots that may use it and 解除配对.

## The desktop client

`desktop/` (A96) is an Electron app with Jarvy's own version (fish m3252–m3253): `.github/workflows/desktop.yml` builds the Windows NSIS installer and the Linux AppImage on GitHub Actions, unsigned, and for a Jarvy release tag (`v*`) puts them into that GitHub Release beside the npm package. `desktop/package.json` stays at 0.0.0; `build.mjs` and `dist.mjs` take the version from the root `package.json`. A client works with other Jarvy versions too: the page comes from Jarvy, and the client only keeps the window and the connection.

- **The page is the web app's**: the window loads Jarvy's own address; nothing of the interface is in the client. `contextIsolation` on, `nodeIntegration` off, `sandbox` on. The preload gives `window.jarvyDesktop` (`src/contract/desktop.ts`: `notify`, `setBadge`, `onOpenChat`, `version`) only to that origin; the page gets no Node. Links elsewhere open in the browser.
- **Trust**: the first run asks for the address and, over HTTPS, shows the root certificate's SHA-256 to compare with Settings › 网络. The window then accepts, for that host, only certificates issued by that root (`setCertificateVerifyProc`), whatever the system trusts.
- **The computer**: once the person signs in on the page, the main process registers the computer with that session (`POST /api/environments/devices`, named after the host) and keeps the token sealed with `safeStorage` (DPAPI on Windows). A computer the command-line connector registered already goes on with its token. The connection is `src/connect/connector.ts`, the same code as `connector.mjs`, in the main process.
- **Tray**: the connection's state and the Bots working here, pause, start at login (off by default), changing the address, quit. Closing the window hides it (said once) and keeps the computer connected; only quitting disconnects it. Unpaired in Jarvy, the tray offers to connect it again rather than doing so by itself.
- **Notifications and count**: the page sends a system notification for a DM or an @ of you from someone else while the window isn't in front (`src/web/desktop.ts`); choosing it opens that chat. The taskbar shows the tab's count (an overlay drawn by the client on Windows).
